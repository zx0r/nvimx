# СПЕЦИФИКАЦИЯ СИСТЕМЫ (SPEC.MD)
**Проект:** Изолированный профильный менеджер и диспетчер среды Neovim (`nvimx`)  
**Архитектурный стандарт:** Data-Oriented Design, Zero-Overhead Process Replacement, Zero-Copy Argv Passthrough, Zero-Dependency Target Architecture

---

## 1. Модель данных и форматы

Система не использует централизованную БД. Все состояние хранится в виде детерминированных файловых структур, конфигурационных манифестов и кэшируемых JSON-реестров.

### 1.1. Форматы хранения на диске

#### 1.1.1. Корневая топология путей (XDG / Windows Base Directory)
Все пути разрешаются через переменные окружения с детерминированными fallback-значениями относительно `$HOME`:

| Сущность | POSIX-спецификация (Linux / macOS) | Windows Native ($LOCALAPPDATA / $TEMP) | Назначение |
|---|---|---|---|
| **Config Root** | `$XDG_CONFIG_HOME/nvim` или `~/.config/nvim` | `%LOCALAPPDATA%\nvim` или `~\AppData\Local\nvim` | Базовая директория профилей по умолчанию |
| **Data Root** | `$XDG_DATA_HOME/nvim` или `~/.local/share/nvim` | `%LOCALAPPDATA%\nvim-data` | Данные плагинов, дерева парсеров Treesitter, shada |
| **State Root** | `$XDG_STATE_HOME/nvim` или `~/.local/state/nvim` | `%LOCALAPPDATA%\nvim-data` (алиас Data Root) | Логи, история поиска, сессии |
| **Cache Root** | `$XDG_CACHE_HOME/nvim` или `~/.cache/nvim` | `%TEMP%\nvim` или `~\AppData\Local\Temp\nvim` | Кэш Lua-байткода, метаданные реестров, песочницы |
| **System Config**| `$XDG_CONFIG_HOME/nvimx` или `~/.config/nvimx` | `%LOCALAPPDATA%\nvimx` | Хранилище `config.toml` самого диспетчера |
| **Sandbox Root** | `$XDG_CACHE_HOME/nvim/sandbox/<profile>` | `%TEMP%\nvim\sandbox\<profile>` | Эфемерные изолированные окружения |
| **Registry Cache**| `$XDG_CACHE_HOME/nvim/registry/` | `%TEMP%\nvim\registry\` | Локальный кэш удаленных реестров |

> **Инвариант адресации профилей:** По умолчанию профиль с именем `$ID` занимает каталог `~/.config/nvim/$ID`. Вторичные директории изолируются через протокол `NVIM_APPNAME` (см. раздел 2).

---

#### 1.1.2. Конфигурационный файл (`~/.config/nvimx/config.toml`)
Формат: TOML v1.0. Порядок ключей произвольный. Все поля опциональны (имеют встроенные значения по умолчанию).

```toml
# Точка входа по умолчанию: имя профиля при запуске без параметров.
# Пустое значение или отсутствие ключа активирует интерактивный селектор (если use_fzf = true).
default_profile = "lazyvim"

# Список URL-адресов удаленных JSON-реестров профилей.
# Fallback обратной совместимости: строковый ключ "registry_url" (scalar string).
registry_urls = [
    "https://raw.githubusercontent.com/zx0r/nvimx-registry/main/index.json"
]

# Использование интерактивного TUI-пикера (fzf) при неопределенности профиля
use_fzf = true

# Уровень гранулярности логов: "debug" | "info" | "warn" | "error"
log_level = "info"

# Формат системного вывода: "text" (ANSI терминал) | "json" (машиночитаемый поток)
output = "text"

# Флаг автоматического обновления бинарного файла диспетчера
auto_update = false

# Автоматическая установка отсутствующего профиля из реестра при вызове setup
auto_install_missing = true

# Режим жесткого отказа: запрет деградации до ванильного nvim при сбоях поиска профиля
strict_mode = false

# Стратегия деградации: запуск неизолированного nvim при отсутствии профиля
fallback_to_plain_nvim = true

# Переопределение каталога хранения профилей.
# Поддерживает синтаксис тильды: "~" -> $HOME, "~/<path>" -> $HOME/<path>.
profiles_dir = "~/.config/nvim"
```

**Инварианты валидации конфигурации:**
1. Если `registry_urls` отсутствует или пуст, парсер ищет строковый скаляр `registry_url`. Если и он отсутствует — подставляется зашитый fallback: `["https://raw.githubusercontent.com/zx0r/nvimx-registry/main/index.json"]`.
2. Пустой или синтаксически поврежденный файл `config.toml` не должен приводить к панике процесса: поля заполняются дефолтными значениями.
3. Разрешение `profiles_dir`:
   - `~` разворачивается в `$HOME`.
   - `~/path` разворачивается в `$HOME/path`.
   - Относительный путь `path` разворачивается относительно текущей рабочей директории.
   - Отсутствие ключа -> возврат `Config Root` (`~/.config/nvim`).

#### 1.1.3. Локальный кэш реестра
Состоит из двух независимых JSON-файлов в директории `$CACHE_ROOT/registry/`:

1. **`data.json`** — Тело реестра:
```json
{
  "profiles": [
    {
      "name": "lazyvim",
      "repo": "https://github.com/LazyVim/starter",
      "type": "starter",
      "default": false
    }
  ]
}
```
*Инварианты валидности `data.json`:*
- Массив `profiles` не должен быть пустым (`len > 0`).
- Значения `name` должны быть уникальными внутри файла (дубликаты запрещены, проверка через дедупликацию множества).
- Поле `type` сериализуется из ключа `"type"`.
- Поле `default` — опциональный булевый флаг (по умолчанию `false`).

2. **`meta.json`** — Метаданные валидности кэша:
```json
{
  "fetched_at": 1740000000,
  "ttl": 3600,
  "url": "https://raw.githubusercontent.com/zx0r/nvimx-registry/main/index.json"
}
```
*Инварианты валидности `meta.json`:*
- `fetched_at`: UNIX Timestamp (uint64) момента сохранения кэша.
- `ttl`: Время жизни в секундах (константа: 3600 с / 1 час).
- Кэш считается валидным, если: `CurrentEpochTime - fetched_at < ttl`.
- При истечении TTL или флаге принудительного обновления (`force_update == true`) выполняется сетевой запрос к удаленному источнику. Если сеть недоступна, система деградирует до чтения устаревшего `data.json` (Stale-While-Revalidate).

---

#### 1.1.4. Формат удаленного API обновлений (GitHub Releases Wire Format)
При вызове обновления бинарника система ожидает от эндпоинта `GET /repos/zx0r/nvimx/releases/latest` минимальный JSON-объект:
```json
{
  "tag_name": "v0.1.3",
  "assets": [
    {
      "name": "nvimx-macos-arm64",
      "browser_download_url": "https://github.com/..."
    }
  ]
}
```
*Инварианты связывания платформ:*
- `macos-arm64`  <= `OS: macos`, `ARCH: aarch64`
- `macos-x86_64` <= `OS: macos`, `ARCH: x86_64`
- `linux-x86_64` <= `OS: linux`, `ARCH: x86_64`

### 1.2. Модель данных в памяти

- **Идентификатор профиля (ProfileId):** Непрерывный срез памяти `&str` / `OsStr`. Ограничение: длина от 1 до 64 байт. Символьный алфавит: строго ASCII `[a-zA-Z0-9_-]`. Не допускаются символы `.`, `/`, `\`, пробелы и управляющие символы (защита от Path Traversal).
- **Массив аргументов (Argv Pool):** Непрерывный `Vec<OsString>`. Никакой транскодировки в UTF-8 при передаче аргументов в дочерний процесс: байты передаются ядру ОС as-is.
- **Зарезервированные системные идентификаторы (12 идентификаторов):**
  `{"list", "install", "clean", "doctor", "setup", "sandbox", "registry", "update", "completions", "help", "repro", "debug"}`.
  Данные строки не могут быть именами профилей. Если пользователь передает зарезервированное имя в качестве аргумента профиля, диспетчер прерывает выполнение с ошибкой (exit code 1).

### 1.3. Полные системные контракты всех 12 подкоманд CLI

Система поддерживает 10 активных функциональных команд и 2 зарезервированных диагностических идентификатора (`repro`, `debug`):

```
nvimx [PROFILE] [FILES...] [-- ARGS...]
nvimx <COMMAND> [FLAGS...] [ARGS...]
```

#### 1.3.1. `list` (Инспекция локальных профилей)
- **Аргументы и флаги:**
  - `--plain`: Булевый флаг. Отключает ANSI-разметку, заголовки и пиктограммы.
- **Поведение:**
  - Сканирует директорию `profiles_dir`.
  - Фильтрует скрытые каталоги (начинающиеся с `.`) и файлы.
  - Сортирует имена профилей лексикографически.
- **Формат вывода:**
  - *Стандартный режим (терминал):*
    ```text
    Profiles
    ✔ astronvim
    ✔ lazyvim
    ✔ nvchad

    ```
    (Заголовок `\nProfiles\n`, пиктограмма `✔` зелёного цвета, пустая строка в конце).
    Если профилей нет: `hint: No profiles detected\n` в stderr (через канал hint).
  - *Режим `--plain` (для shell-скриптов и конвейеров):*
    ```text
    astronvim
    lazyvim
    nvchad
    ```
    (Только имена профилей, разделенные `\n`, без ANSI-кодов и без завершающей пустой строки).
- **Код возврата (Exit Code):** `0` (успех или отсутствие профилей), `1` при невосстановимой ошибке чтения файловой системы.

---

#### 1.3.2. `install` (Установка профиля)
- **Аргументы и флаги:**
  - `<repo>`: Обязательный позиционный аргумент. URL git-репозитория (`https://...`, `git@...`, `user/repo`) или короткое имя профиля из реестра (например, `lazyvim`).
  - `<name>`: Обязательный позиционный аргумент. Целевое имя директории профиля.
- **Поведение:**
  - Валидация имени: проверка на запрещенные символы и принадлежность к 12 зарезервированным именам. При совпадении с зарезервированным именем: вывод ошибки в stderr `✘ Name '<name>' is reserved` и завершение.
  - Проверка коллизий: если каталог `profiles_dir / name` уже существует — вывод `✘ Profile already exists` в stderr.
  - Резолвинг источника: если аргумент `<repo>` не содержит `://` и `@`, выполняется поиск в кэше реестра. При совпадении подставляется URL из поля `repo`. Если URL всё ещё не содержит протокол, выполняется нормализация вида `https://github.com/<repo>`.
  - Клонирование: попытка shallow-clone через GitHub CLI:
    `gh repo clone <repo> <dest> -- --depth 1` (stdout/stderr подавлены).
    При отсутствии `gh` или ошибке — fallback на:
    `git clone --depth 1 <repo> <dest>`.
- **Формат вывода:**
  - При старте: `==> Fetching downloads for: <url>` (`==>` cyan bold).
  - При успехе: `✔ done` (green).
  - При ошибке: `✘ Installation failed` в stderr.
- **Код возврата (Exit Code):** `0` при успешной установке, `1` при ошибке клонирования или валидации.

---

#### 1.3.3. `clean` (Интерактивная деструктивная очистка)
- **Аргументы и флаги:**
  - `<profile>`: Обязательный позиционный аргумент. Имя профиля для удаления.
- **Поведение:**
  - Сканирует 4 изолированных каталога профиля: Config, Data, State, Cache.
  - Если ни один каталог не найден: вывод информационного сообщения `nothing to clean` (dimmed) и немедленный возврат.
  - Формирует список существующих каталогов с заменой префикса `$HOME` на `~`.
  - Выводит предупреждение и интерактивный запрос `Proceed? [y/N]: ` (без переноса строки, с принудительным `flush`).
  - Ожидает строку из `stdin`. Если ответ не равен `y` / `Y` (регистронезависимо): выводит `cleanup cancelled` (dimmed) и выходит.
  - При подтверждении стирает интерактивный блок в TTY через ANSI-последовательности (см. раздел 4.2) и рекурсивно удаляет каталоги через системный вызов удаления директорий.
- **Формат вывода:**
  ```text
  Cleaning lazyvim...
  warning: the following directories will be deleted:
    • ~/.config/nvim/lazyvim
    • ~/.local/share/nvim/lazyvim
    • ~/.local/state/nvim/lazyvim
    • ~/.cache/nvim/lazyvim

  Proceed? [y/N]: y
  ✔ Config → ~/.config/nvim/lazyvim
  ✔ Data → ~/.local/share/nvim/lazyvim
  ✔ State → ~/.local/state/nvim/lazyvim
  ✔ Cache → ~/.cache/nvim/lazyvim

  ✔ lazyvim cleaned
  ```
- **Код возврата (Exit Code):** `0` (успех или отмена пользователем), `1` при сбое удаления каталогов.

---

#### 1.3.4. `doctor` (Диагностика окружения)
- **Аргументы и флаги:**
  - `--json`: Булевый флаг. Активирует строгий машиночитаемый JSON-вывод.
- **Проверяемые подсистемы и инварианты:**
  1. `nvim`: вызов `nvim --version`, парсинг первого токена версии (`v0.10.x`). Статус: `ok` если найден, `error` если отсутствует.
  2. `git`: вызов `git --version`. Статус: `ok` если найден, `error` если отсутствует.
  3. `fzf`: вызов `fzf --version`. Статус: `ok` если найден, `warn` если отсутствует.
  4. `config`: проверка наличия `~/.config/nvimx/config.toml` и чтение `default_profile`. Статус: всегда `ok`.
  5. `registry`: проверка HTTP GET доступности первого URL из `registry_urls` (таймаут 2.0 с). Статус: `ok` при HTTP 200, `error` при сбое сети, `warn` если список URL пуст.
  6. `profiles`: подсчет установленных профилей в `profiles_dir`. Статус: `ok` при `count > 0`, `warn` при `count == 0`.
- **Машиночитаемый формат (`--json`):**
  Строго соответствует JSON-схеме (значения полей строго `"ok"`, `"warn"`, `"error"`):
  ```json
  {
    "nvim": "ok",
    "git": "ok",
    "fzf": "ok",
    "config": "ok",
    "registry": "ok",
    "profiles": "ok"
  }
  ```
- **Формат вывода в терминале (Human-Readable):**
  ```text
  Environment:
    ✔ nvim             v0.10.4
    ✔ git              2.48.1
    ✔ fzf              found

  Configuration:
    ✔ config           ~/.config/nvimx/config.toml
    ✔ default_profile  lazyvim

  Registry:
    ✔ registry         reachable (https://raw.githubusercontent.com/...)

  Profiles:
    ✔ profiles         3 installed

  result: ✔ ok
  ```
  Итоговый вердикт `result:`:
  - `✖ error` (красный): если `nvim == error || git == error || registry == error`.
  - `⚠ warn` (желтый): если ошибки отсутствуют, но `fzf == warn || profiles == warn`.
  - `✔ ok` (зеленый): если все компоненты имеют статус `ok`.
- **Код возврата (Exit Code):** `0` (включая режим предупреждений), `1` только при критическом сбое I/O / сериализации.

#### 1.3.5. `setup` (Инициализация и интеграция с оболочкой)
- **Синтаксис вызова:**
  - `nvimx setup [--force]`
  - `nvimx setup shell [FLAGS...]`
- **Флаги верхнего уровня:**
  - `--force`, `-f`: Принудительная перезапись существующего `config.toml` (с созданием резервной копии `config.toml.bak`).
- **Подкоманда `setup shell` (Флаги интеграции):**
  - `--override-nvim`: Встраивает функцию-перехватчик `nvim()` в rc-файл оболочки для прозрачного вызова `nvimx`.
  - `--force-env`: Перезапись переменных окружения `EDITOR`/`VISUAL`.
  - `--print-env`: Вывод экспорт-блока переменных окружения в stdout без записи на диск.
  - `--print`: Вывод полного shell-скрипта (обертка + переменные) в stdout.
  - `--dry-run`: Симуляция применения изменений без записи файлов.
  - `--remove`: Удаление интеграции из rc-файлов.
- **Поведение базового `setup`:**
  1. Проверяет наличие в `$PATH` утилит `git` и `nvim`. Если хотя бы одна отсутствует — завершение с сообщением `✘ missing essential dependencies`.
  2. Проверяет наличие `config.toml`. При отсутствии создает шаблонный файл со стандартными параметрами. При `--force` делает бэкап.
  3. Проверяет существование каталога `profiles_dir`. Создает его при отсутствии.
  4. Проверяет наличие `default_profile` на диске. Если профиль отсутствует — предлагает интерактивную установку `Proceed with installation? [Y/n]: ` и при согласии устанавливает его из реестра.
- **Интеграция с оболочками (Fish / Zsh / Bash):**
  - Автоопределение типа оболочки через чтение `$SHELL`.
  - Пути автодополнений:
    - Fish: `~/.config/fish/completions/nvimx.fish`
    - Zsh: `~/.zsh/completions/_nvimx`
    - Bash: `~/.bash_completion.d/nvimx`
  - Функция-обертка Neovim: перехватывает вызовы `nvim`. Если первый аргумент начинается с дефиса (`-`) или уже установлена переменная `NVIM_APPNAME` — управление передается реальному `command nvim`. Иначе управление передается `nvimx`.
- **Код возврата (Exit Code):** `0` при успешной настройке, `1` при отсутствии зависимостей или неподдерживаемой оболочке.

---

#### 1.3.6. `sandbox` (Эфемерный запуск)
- **Аргументы и флаги:**
  - `<profile>`: Обязательный позиционный аргумент. Имя профиля из реестра или URL git-репозитория.
- **Поведение:**
  - Создает изолированное дерево каталогов в `$CACHE/nvim/sandbox/<profile>`:
    `config/nvim`, `data`, `state`, `cache`.
  - При наличии старого каталога песочницы — производит его полную зачистку (`rm -rf`).
  - Разрешает имя репозитория через реестр (если передан короткий идентификатор).
  - Клонирует конфигурацию с глубиной 1 в `<sandbox>/config/nvim`.
  - Запускает `nvim` в синхронном режиме ожидания (`wait`), изолируя все XDG-пути и выставляя заголовок терминала `set title titlestring=nvimx\ sandbox:\ <profile>`.
- **Формат вывода:**
  ```text
  Sandbox: lazyvim
  ✔ Resolved to: https://github.com/LazyVim/starter
  Cloning profile into sandbox...
  ✔ Launching Neovim (sandbox: lazyvim)
  ✔ Sandbox session ended
  ```
- **Код возврата (Exit Code):** Код завершения процесса `nvim` (обычно `0`), `1` при ошибке клонирования.

---

#### 1.3.7. `registry` (Управление реестрами профилей)
- **Синтаксис вызова:**
  - `nvimx registry list`: Вывод списка сконфигурированных реестров в stdout.
    Формат: `\nRegistries:\n  • <url>\n\n`.
  - `nvimx registry check`: Валидация доступности и схемы каждого реестра.
    Формат: `✔ <url> reachable` или `✘ <url> failed (<error>)`.
  - `nvimx registry update`: Принудительное сетевое обновление кэша `data.json` и `meta.json`.
    Формат: `✔ cache updated` или `✘ failed to update: <error>`.
  - `nvimx registry cache clear`: Удаление локальных файлов кэша из дискового пространства.
    Формат: `✔ registry cache cleared`.
- **Код возврата (Exit Code):** `0` при успехе, `1` при сетевых ошибках или сбоях валидации.

---

#### 1.3.8. `update` (Самообновление бинарника)
- **Аргументы и флаги:** Без дополнительных аргументов.
- **Поведение:**
  - Проверка Homebrew: если путь к текущему исполняемому файлу содержит `Cellar` или `homebrew`, самообновление блокируется:
    ```text
    ✔ nvimx is managed by homebrew
    hint: run 'brew upgrade nvimx' to update
    ```
    Завершение с кодом `0`.
  - Запрос к GitHub API: получение метаданных последнего релиза.
  - Сравнение версий: парсинг SemVer. Если текущая версия актуальна — печать `✔ nvimx is up to date (vX.Y.Z)` и выход с кодом `0`.
  - Скачивание: выбор бинарного ассета под `OS-ARCH` системы, загрузка временного файла в директорию целевого бинарника (см. фикс в разделе 4.5), назначение прав исполнения `0o755` и атомарная замена через замену пути.
- **Формат вывода:**
  ```text
  update
  ✔ checking for updates...
  ✔ new version available: v0.2.0 (current: v0.1.3)
  ✔ downloading...
  ✔ installing...
  ✔ updated to v0.2.0
  ```
- **Код возврата (Exit Code):** `0` при успешном обновлении или отсутствии обновлений, `1` при сетевом сбое или отказе в доступе к ФС.

### 2.1. Главный горячий путь: `nvimx [PROFILE] [FILES...] [-- ARGS...]`
Критический путь запуска целевого редактора.

**Требования к производительности:**
- **Задержка запуска (Startup Overhead):** $\le 15.0$ миллисекунд (контролируется тестом 4 в E2E-сьюте).
- **Аллокации в куче:** Максимально плоские. Парсинг CLI-флагов без реаллокаций строк аргументов.
- **Модель выполнения:** Замена текущего процесса через системный вызов `execvp` (`std::os::unix::process::CommandExt::exec`). Диспетчер **не остается** висеть в памяти родительским процессом и не осуществляет супервизинг stdio.

#### 2.1.1. Быстрый путь (Fast-Path bypass)
Если первым аргументом является `-v`, `-V`, `--version` или `help` / `--help`:
Система производит вывод статических данных без обращения к дисковой подсистеме (`config.toml` не читается, 0 обращений к ФС) и завершает работу с кодом `0`.

#### 2.1.2. Алгоритм разрешения первого аргумента (0-Cost Disambiguation):
```
Если first_arg присутствует:
    Если first_arg в списке 12 зарезервированных команд:
        -> Переход к обработчику подкоманды (или ошибка для repro/debug)
    Иначе если is_valid_profile_name(first_arg) И dir_exists(profiles_dir / first_arg):
        -> profile_name = first_arg
        -> target_args  = rest_args
    Иначе:
        # Аргумент интерпретируется как файл или флаг для Neovim
        -> profile_name = config.default_profile
        -> target_args  = [first_arg] + rest_args
Иначе:
    -> profile_name = config.default_profile
    -> target_args  = rest_args
```

### 2.2. Маппинг `profiles_dir` на `NVIM_APPNAME` и `XDG_CONFIG_HOME`

В механизме изоляции Neovim внутренний путь к конфигурации вычисляется ядром Neovim по правилу:
$$\text{Config Path} = \$XDG\_CONFIG\_HOME / \$NVIM\_APPNAME$$
*(где при отсутствии переменной $XDG\_CONFIG\_HOME используется значение по умолчанию `~/.config`).*

#### Системный инвариант целевой архитектуры:
При запуске профиля диспетчер обязан гарантировать, что фактическая директория профиля на диске строго совпадает с вычисленной Neovim директорией конфигурации.

1. **Стандартный режим (`profiles_dir` не переопределен или равен дефолтному `~/.config/nvim`):**
   - Переменная `XDG_CONFIG_HOME` сохраняется без изменений (наследуется из окружения пользователя).
   - Выставляется переменная окружения:
     $$\text{NVIM\_APPNAME} = \text{"nvim/"} + \text{profile\_name}$$
   - В результате Neovim обращается к:
     - Config: `~/.config/nvim/<profile_name>`
     - Data: `~/.local/share/nvim/<profile_name>`
     - State: `~/.local/state/nvim/<profile_name>`
     - Cache: `~/.cache/nvim/<profile_name>`
   *(Идеальное соответствие соглашению Neovim 0.9+).*

2. **Пользовательский режим (`profiles_dir` переопределен в `config.toml` на нестандартный путь):**
   - Пусть `profiles_dir = Path("/custom/storage/my-profiles")`.
   - Диспетчер вычисляет родительский каталог и базовое имя:
     $$\text{Base Dir} = \text{profiles\_dir.parent()}$$
     $$\text{Folder Name} = \text{profiles\_dir.file\_name()}$$
   - Выставляются переменные:
     $$\text{XDG\_CONFIG\_HOME} = \text{Base Dir}$$
     $$\text{NVIM\_APPNAME} = \text{Folder Name} + \text{"/"} + \text{profile\_name}$$
   - *Результат:* Neovim вычисляет `$XDG_CONFIG_HOME/$NVIM_APPNAME` $\rightarrow$ `/custom/storage/my-profiles/<profile_name>`, обеспечивая 100% изоляцию даже при размещении профилей на внешних точках монтирования или нестандартных каталогах.

3. **Режим Vanilla (профиль не задан и fallback активен):**
   - Переменная `NVIM_APPNAME` удаляется из таблицы окружения (`cmd.env_remove("NVIM_APPNAME")` / `unsetenv`).
   - Neovim запускается с ванильной конфигурацией по умолчанию (`~/.config/nvim`).

---

### 2.3. Путь интерактивного выбора (TUI-селектор через `fzf`)
Активируется, если профиль не был указан на входе и не задан `default_profile` (либо задан несуществующий профиль при `use_fzf = true`).

1. **Сканирование каталога `profiles_dir`:**
   - Чтение записей каталога через `read_dir`.
   - Проверка `file_type().is_dir()` (без отдельного вызова `stat` на Unix).
   - Фильтрация: исключаются скрытые папки (начинающиеся с `.`) и служебные (начинающиеся с `_`).
2. **Пайплайн дочернего процесса:**
   - Порождение процесса `fzf` с флагами:
     `--header "Select Neovim Profile (ESC to cancel)" --height 40% --layout reverse --border --color "header:italic:cyan,pointer:bold:green,hl:bold:yellow" --prompt "λ "`
   - Потоки: `stdin: Piped`, `stdout: Piped`, `stderr: Inherit` (отрисовка TUI напрямую в терминал).
3. **Передача данных:** Запись отфильтрованных имен профилей в stdin `fzf` с разделителем `\n`. Закрытие (`drop`) дескриптора stdin для сигнализации EOF.
4. **Захват результата:**
   - Код возврата `0`: Считывание stdout, обрезка пробельных символов `\r\n` -> переход на горячий путь `execvp("nvim")`.
   - Код возврата `!= 0` (пользователь нажал ESC / прервал): Вывод `picker cancelled` (dimmed) и выход с кодом `0` без запуска Neovim.

---

### 2.4. Путь изоляции «Песочница» (Sandbox Pipeline)
Запуск профиля с полной изоляцией не только конфигурации, но и глобальных путей XDG.

1. **Создание эфемерной структуры директорий:**
   `$CACHE/nvim/sandbox/<profile>/{config/nvim, data, state, cache}`.
   *Если директория существовала — она рекурсивно удаляется (`rm -rf`) перед стартом.*
2. **Получение конфигурации:**
   - Разрешение имени через локальный/удаленный реестр.
   - Клонирование репозитория с глубиной 1: `gh repo clone <repo> <sandbox>/config/nvim -- --depth 1` (fallback на `git clone --depth 1`).
3. **Изоляция через подмену XDG-окружения:**
   ```bash
   XDG_CONFIG_HOME = "<sandbox>/config"
   XDG_DATA_HOME   = "<sandbox>/data"
   XDG_STATE_HOME  = "<sandbox>/state"
   XDG_CACHE_HOME  = "<sandbox>/cache"
   NVIM_APPNAME    = "nvim"
   NVIMX_SANDBOX   = "<profile>"
   ```
4. **Запуск и супервизинг:**
   Вызов `nvim --cmd "set title titlestring=nvimx\ sandbox:\ <profile>"`.
   В отличие от Hot Path, здесь вызывается `fork + wait` (`Command::status`), диспетчер блокируется до завершения сеанса Neovim, после чего выводит подтверждение закрытия песочницы.

### 3.1. Глобальная диаграмма состояний приложения

```
             ┌─────────────────────────┐
             │       [INIT / S0]       │
             │ Парсинг CLI + Config    │
             └────────────┬────────────┘
                          │
          ┌───────────────┴───────────────┐
          │                               │
          ▼                               ▼
 ┌─────────────────┐             ┌─────────────────┐
 │   [SUB_CMD]     │             │  [RESOLVE / S1] │
 │ Обработка команд│             │ Анализ профиля  │
 └─────────────────┘             └────────┬────────┘
                                          │
                     ┌────────────────────┼────────────────────┐
                     │                    │                    │
      [Профиль валиден и найден]  [Не найден]            [Не указан]
                     │                    │                    │

              ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
```

### 3.2. Таблица переходов конечного автомата

| Текущее состояние | Входное событие / Условие | Целевое состояние | Сайд-эффекты и системные действия |
|---|---|---|---|
| **S0 (Init)** | Передан `-v` / `-V` / `--version` | **Exit (0)** | Вывод версии и платформы в stdout, мгновенный выход (0 syscalls к диску). |

| **S1 (Resolve)** | Профиль не указан И `use_fzf == true` | **S4 (Picker)** | Проверка существования `profiles_dir`, создание при отсутствии, вызов `fzf`. |
| **S1 (Resolve)** | Профиль не указан И `use_fzf == false` | **S3 (Vanilla)** | Удаление `NVIM_APPNAME` из окружения, прямой запуск `nvim`. |
| **S4 (Picker)** | Пользователь выбрал элемент (`fzf exit 0`) | **S3 (Launch)** | Захват имени из stdout, установка `NVIM_APPNAME`, вызов `execvp`. |
| **S4 (Picker)** | Отмена выбора (`fzf exit != 0`) | **Exit (0)** | Печать `picker cancelled` в stdout, нормальный выход без запуска редактора. |
| **S_CMD (Clean)**| Запрос очистки профиля | **Prompt** | Сканирование 4-х путей XDG, вывод списка, запрос `[y/N]`. |

| **Prompt (Clean)**| Ввод `!= y` | **Exit (0)** | Печать `cleanup cancelled`, нормальный выход. |

## 4. Граничные случаи и системные контракты (Edge Cases)

### 4.1. Контракт замены процесса (POSIX Process Image Replacement)
1. **Отсутствие возврата:** На Unix-системах вызов `execvp` физически заменяет образ процесса в таблице ОС. Все открытые дескрипторы (за исключением помеченных `O_CLOEXEC`), переменные окружения и сигнатурные маски наследуются процессом Neovim.
2. **Нулевой оверхед диспетчера:** Память, занятая диспетчером, полностью высвобождается ядром в момент вызова `execvp`. Задержка равна времени системного вызова ядра на загрузку бинарного заголовка `nvim`.

---

### 4.2. Межпроцессное взаимодействие и терминал (TTY / ANSI Contracts)

#### 4.2.1. Деструктивный TTY-откат в `clean`
При подтверждении очистки диспетчер очищает ранее выведенный блок предупреждения и интерактивного ввода. Выполняется вывод в stdout escape-последовательностей ANSI:
```
\x1b[A  # Перемещение курсора на одну строку вверх
\x1b[2K # Полная очистка текущей строки
```
Последовательность повторяется ровно $N + 3$ раз, где $N$ — число найденных для удаления каталогов.

> [!WARNING] **[LEGACY DEFECT -> FIX IN TARGET ARCHITECTURE]**  
> **Дефект:** В легаси-коде вывод управляющих ANSI-последовательностей выполняется безусловно. Если `clean` вызывается в non-interactive окружении, скрипте или через пайп, в поток попадают сырые бинарные escape-байты `\x1b[A\x1b[2K`.  
> **Требование целевой архитектуры:** Использовать стандартную проверку `std::io::stdout().is_terminal()`. При отсутствии TTY интерактивный опрос отключается (требуется флаг `--yes` / `-y`), а ANSI-очистка экрана подавляется.

#### 4.2.2. Управление цветом и форматированием
> [!WARNING] **[LEGACY DEFECT -> FIX IN TARGET ARCHITECTURE]**  
> **Дефект:** Вывод цветов в легаси-коде генерировался статически через крейт `owo-colors` без проверки переменной окружения `NO_COLOR` и без проверки `is_terminal()`.  
> **Требование целевой архитектуры:** Диспетчер обязан проверять:
> 1. Наличие переменной окружения `NO_COLOR` (если задана — цвет полностью отключается).
> 2. `std::io::stdout().is_terminal()` и `std::io::stderr().is_terminal()`. При перенаправлении в файл или пайп ANSI-коды цветов не должны попадать в поток.

#### 4.2.3. Безопасность аргументов (Null-byte & Lossy Path Traversal)
При проверке существования профиля на диске аргумент конвертируется через `to_string_lossy()`. Однако в финальный системный вызов `execvp` аргументы передаются как исходные `OsString`, сохраняя оригинальные последовательности байт целевой ОС.

---

### 4.3. Системные инварианты файловой системы и блокировки

#### 4.3.1. Отсутствие файловых блокировок (No File Locks)
В системе нет блокировок (`flock`/`fcntl`). Параллельный запуск двух инстансов с одинаковым отсутствующим профилем приведет к состоянию гонки при клонировании каталога или записи кэша реестра.

#### 4.3.2. Рассинхронизация адресации профилей при очистке
> [!WARNING] **[LEGACY DEFECT -> FIX IN TARGET ARCHITECTURE]**  
> **Дефект:** В легаси-кодовой базе команды `run`, `install`, `list`, `setup` используют единую функцию разрешения `get_profiles_dir()` (учитывающую переопределение `profiles_dir` в `config.toml`), тогда как команда `clean` удаляла профиль строго из стандартного `xdg::config_root().join(profile)`. Если пользователь изменял каталог профилей на `~/my-profiles`, команда `clean` удаляла профиль из `~/.config/nvim`, не затронув реальные файлы!  
> **Требование целевой архитектуры:** Команда `clean` обязана использовать **единый резолвер директории профилей**, разрешая каталог конфигурации строго через `profiles_dir / profile`.

#### 4.3.3. Безусловная перезапись песочницы
Команда `sandbox` не выполняет проверку содержимого каталога `$CACHE/nvim/sandbox/<name>`: при наличии каталога он уничтожается рекурсивно через `remove_dir_all`.

### 4.4. Обработка сигналов ОС
- В приложении не регистрируются собственные обработчики сигналов (`SIGINT`, `SIGTERM`, `SIGHUP`).
- Во время ожидания ввода в интерактивных запросах (`[y/N]`) нажатие `Ctrl+C` приводит к стандартному завершению процесса ядром через `SIGINT` (код 130).
- При вызове Neovim сигналы целиком передаются новому бинарнику через замещение процесса (`execvp`).

### 4.5. Атомарная замена бинарника и межфайловый перенос (Cross-Device Links)

> [!WARNING] **[LEGACY DEFECT -> FIX IN TARGET ARCHITECTURE]**  
> **Дефект:** При самообновлении (`update`) легаси-код создавал временный файл рядом или в системном каталоге и вызывал `fs::rename(tmp, current_exe)`. При ошибке `rename` код немедленно вызывал `sudo mv`. На Unix-системах, если временный каталог смонтирован на `tmpfs`, а бинарник лежит на физическом диске (`ext4`/`btrfs`/`apfs`), системный вызов `rename(2)` **всегда возвращает ошибку `EXDEV` (Invalid cross-device link, os error 18)** даже при полных правах пользователя! Вызов `sudo` в этом случае являлся грубой ошибкой проектирования.  
> **Требование целевой архитектуры:**
> 1. Временный файл скачивается строго в ту же родительскую директорию, где находится текущий исполняемый файл: `current_exe.parent().join(".nvimx-update.tmp")`. В этом случае замена гарантированно происходит в пределах одной файловой системы и выполняется атомарно через системный вызов `rename(2)`.
> 2. При возврате ошибки ядра `EXDEV` диспетчер обязан выполнить неразрушающий перенос: `fs::copy(tmp, current_exe)` с последующим `fs::remove_file(tmp)`.
> 3. Внешний вызов `sudo mv` допускается строго и исключительно при получении ошибки `EACCES` / `EPERM` (Permission Denied).

### 4.6. Контракт E2E-валидации (`tests/e2e/validate.sh`)

Для гарантии 100% бинарной и поведенческой совместимости новая реализация обязана проходить полный набор тестов скрипта `tests/e2e/validate.sh` без модификации самого тестового файла.

| № | Название теста в `validate.sh` | Точная команда вызова | Проверяемый инвариант и assert | Критерий прохождения |
|---|---|---|---|---|
| **1** | **Exact argv passthrough** | `$NVIMX "$TEST_PROFILE" --headless -c 'lua print(table.concat(vim.v.argv, " "))' +qa 2>&1` | Проброс неизмененных аргументов через границу процесса в `vim.v.argv` Neovim. | `OUT` содержит подстроку `"--headless"` |
| **2** | **NVIM_APPNAME isolation** | `$NVIMX "$TEST_PROFILE" --headless --cmd 'lua print(vim.env.NVIM_APPNAME or "")' +qa 2>&1` | Корректная установка переменной окружения `NVIM_APPNAME`. | `OUT` содержит подстроку `"$TEST_PROFILE"` (например, `nvim/lazyvim`) |
| **3** | **XDG config path mapping** | `$NVIMX "$TEST_PROFILE" --headless --cmd 'lua print(vim.fn.stdpath("config"))' +qa 2>&1` | Разрешение внутреннего пути Neovim `stdpath("config")` в каталог профиля. | `OUT` содержит подстроку `"$TEST_PROFILE"` |
| **4** | **Startup overhead benchmark** | `$NVIMX "$TEST_PROFILE" --headless -c 'lua local t=vim.uv.hrtime(); vim.defer_fn(function() io.write(string.format("%.2f",(vim.uv.hrtime()-t)/1e6)) end,0)' +qa 2>&1` | Задержка диспетчера при холодном старте. Парсинг первого вещественного числа из stdout через regex `[0-9]+\.[0-9]+`. | Измеренное время `$TIME < 15.00` мс (локально) или `< 300.00` мс (CI) |
| **5** | **Headless LSP init** | `$NVIMX "$TEST_PROFILE" --headless -c 'lua local ok,_=pcall(vim.lsp.start,{name="val",cmd={"echo"},root_dir=vim.fn.getcwd()}); vim.wait(200,function() return #vim.lsp.get_clients({name="val"})>0 end); vim.print(ok)' +qa 2>&1` | Корректное наследование дескрипторов stdio и работоспособность асинхронного цикла событий Neovim. | `OUT` содержит подстроку `"true"` |
| **6** | **IPC server readiness** | `$NVIMX "$TEST_PROFILE" --headless --listen "$SOCK" </dev/null >/dev/null 2>&1 &`<br>затем опрос:<br>`nvim --server "$SOCK" --remote-expr '"IPC_OK"'` | Работа фонового процесса Neovim, открытие Unix Domain Socket и ответ на IPC RPC запросы. | `IPC_OUT` содержит подстроку `"IPC_OK"` |

**Инвариант кода завершения тестового сьюта:**
- При успешном прохождении всех 6 проверок: скрипт выводит `🏆 SUCCESS: All 6 tests passed!` и завершается с кодом `0`.
- При сбое хотя бы одного теста: скрипт выводит `💥 FAILED: X tests failed` и завершается с кодом `1`.

## 5. Внешние зависимости и Zero-Dependency Blueprint

Архитектурный аудит библиотек и план перехода на чистую реализацию без транзитивного оверхеда.

### 5.1. Аудит используемых зависимостей

| Крейт | Фактическая роль в коде | Статус архитектурной необходимости | Альтернатива на базе `std` / Zero-Dep |
|---|---|---|---|
| **`clap`** + **`clap_complete`** | Парсинг CLI-дерева, генерация completions | **Условно-избыточный.** Добавляет ~1.2 МБ к бинарнику. | Ручной разбор `std::env::args_os()` через плоский pattern matching. 0 аллокаций, задержка старта < 0.1 мс. Статические строки completions встраиваются через `include_str!`. |
| **`serde`** + **`serde_json`** + **`toml`** | Десериализация `config.toml`, кэша реестра и вывода `doctor` | **Избыточный для TOML.** | Для `config.toml` — легковесный построчный сканер ключей `key = value` на 40 строк кода без рефлексии. Для `doctor --json` и кэша реестра — компактная сериализация через стандартный `write!`. |
| **`ureq`** | Синхронные HTTP-запросы (реестр, GitHub API) | **Тяжелый сетевой стек.** Тянет TLS-стек `rustls`/`ring` (~1.5 МБ кода, десятки транзитивных крейтов). | Вызов системного бинарника `curl -fsSL` через `std::process::Command` (утилиты `git` и `gh` уже являются обязательными зависимостями системы). Полное исключение TLS-стека из бинарника. |
| **`dirs`** | Кроссплатформенный поиск home directory | **Избыточный.** | Чтение переменной окружения `$HOME` на Unix и `%USERPROFILE%` на Windows средствами `std::env::var_os`. |
| **`which`** | Поиск бинарников `git`, `nvim` в `$PATH` | **Избыточный.** | Итерация по путям `std::env::split_paths(&std::env::var_os("PATH"))` с проверкой `path.join(bin).is_file()`. |
| **`semver`** | Сравнение версий при самообновлении | **Избыточный.** | Парсинг трех чисел `(u32, u32, u32)` через разделители `.` без внешних библиотек. |
| **`indicatif`** | Отрисовка прогресс-бара при скачивании | **Косметический оверхед.** | Вывод символа возврата каретки `\r` с процентами в `stderr` через стандартный буфер `std::io::Write`. |
| **`owo-colors`** | ANSI цвета для терминала | **Косметический.** | Константные escape-строки (`\x1b[32m` и т.д.) через макросы без рантайм-вычислений. |
| **`tracing`** + **`tracing-subscriber`** | Системные зависимости в `Cargo.toml` | **Мертвый код (Dead Weight).** Подписчик не инициализируется ни в одной точке кода. | Полное удаление из манифеста. |
| **`chrono`** | Работа со временем | **Мертвый код.** Не используется в исходниках (время берется через `SystemTime::now()`). | Полное удаление из манифеста. |
| **`thiserror`** | Определение типов ошибок | **Избыточный.** | Реализация `std::fmt::Display` и `std::error::Error` вручную. |
| **`anyhow`** | Универсальный `Result<T>` для команд | **Допустим для CLI.** | Для максимального контроля задержек предпочтителен компактный перечислитель ошибок `Result<T, SystemError>`. |

### 5.2. Целевой Zero-Dependency профиль артефакта
При отказе от внешних зависимостей в пользу стандартной библиотеки `std`:
- Размер скомпилированного stripped release бинарника: **$\sim 300-400$ КБ** (вместо 4.2 МБ).
- Время полной сборки с нуля (`cargo build --release`): **$< 1.5$ секунд** (вместо 25+ секунд).
- Накладные расходы диспетчера на холодном старте: **$< 1.0$ миллисекунды** (в 15 раз быстрее жесткого лимита E2E-теста).
- Изоляция от уязвимостей в цепочке поставок (Supply Chain Security): 0 внешних зависимостей.
